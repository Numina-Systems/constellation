# Anthropic prompt-cache breakpoint audit (issue #38)

**Audit date:** 2026-09-28  
**Issue:** #38  
**Audited branch:** `fix/issues-38-49`

This report describes the `cache_control` placement in the current tree and evaluates its behavior across requests. The adapter code and relevant call paths were inspected directly; citations below refer to the source line numbers verified on 2026-09-28. The audit did not call Anthropic or attempt to measure live cache-hit rates, so impact estimates are qualitative.

## Placement map

| Request component | Current placement | Source evidence |
|---|---|---|
| Anthropic `system` | `buildAnthropicSystemParam` combines `request.system` and any system-role message text in order, joins them with double newlines, and emits one text block with `cache_control: {type: "ephemeral"}`. If there is no system content, it emits no system parameter and no breakpoint there. | `src/model/anthropic.ts:30-67` |
| Messages | `buildRequestParams` removes system-role messages, normalizes the rest, then calls `applyCacheControlToLastBlock`. That helper marks the final content block of the final message. If that message has string content, it first wraps it as one text block; if the message array is empty, it does nothing. | `src/model/anthropic.ts:69-87`, `src/model/anthropic.ts:99-114` |
| Tool definitions | Tool definitions are normalized by mapping their fields; no `cache_control` is added to a tool or schema. | `src/model/anthropic.ts:116-124` |
| Other request fields | No other `cache_control` emission site exists in the adapter. Both `complete()` and `stream()` use `buildRequestParams` and send the resulting `system`, `tools`, and `messages` fields. | `src/model/anthropic.ts:99-114`, `src/model/anthropic.ts:223-243`, `src/model/anthropic.ts:295-315` |

The emitted breakpoint locations are therefore exactly the system text block (when present) and the final message’s final content block (when a non-system message exists). The implementation’s stated ordering assumption is that Anthropic considers tools before system and messages; accordingly the system breakpoint is intended to cover the tool definitions plus system text, and the message breakpoint extends the reusable conversation prefix (`src/model/anthropic.ts:3-7`).

## Breakpoint budget

Anthropic permits at most four `cache_control` breakpoints per request. In the normal agent request—with nonempty system text and at least one non-system message—the adapter emits **two of four**, leaving two unused (`src/model/anthropic.ts:60-66`, `src/model/anthropic.ts:76-86`). With system text but no non-system messages, it emits one; without system text but with messages, it emits one; with neither, it emits none (`src/model/anthropic.ts:56-67`, `src/model/anthropic.ts:72-86`). The existing AC6.3 tests explicitly assert two markers with a system prompt and one without it (`src/model/anthropic.test.ts:605-664`).

The count is stable for a given request shape, not unconditionally stable across requests: an absent system parameter, an empty message list, or changing between those shapes changes the count. In the steady-state multi-turn/tool-enabled agent case, the expected shape has system text and conversation messages, so the count remains two. No tool breakpoint is currently spent; simply using more tools does not increase the count.

Using fewer than the four available markers is not itself a defect. Each additional marker should be placed only at a useful, repeatable prefix boundary. The existing second marker is already request-relative and is used to mark the end of the current conversation prefix.

## Cross-turn prefix stability

### System and tool prefix

The agent builds the system prompt anew in each model round from `buildSystemPrompt(memory)` and appends the optional diary section. Dynamic recall, skills, and working-memory sections are deliberately not placed in this prompt (`src/agent/agent.ts:397-403`, `src/agent/context.ts:14-24`). `buildSystemPrompt` calls the memory manager; the production manager reads core blocks and formats their labels and content in returned order (`src/memory/manager.ts:59-71`). Thus the prompt is byte-stable when core block content/order and the diary value remain unchanged, but changes to core memory or diary text naturally change the prefix. Re-fetching/rebuilding is not evidence that the bytes changed; it does mean stability depends on those inputs remaining the same.

Tools are supplied separately from the system text. The agent obtains them from `registry.toModelTools()` for each round (`src/agent/agent.ts:472`); the registry maps its insertion-ordered `Map` values directly into model tool definitions (`src/tool/registry.ts:147-177`). The Anthropic adapter preserves that supplied order (`src/model/anthropic.ts:116-124`). A tool addition, removal, replacement, schema change, or reorder can therefore change the prefix covered by the system breakpoint. Tool ordering is deterministic for a stable registry, but it is not canonicalized at the adapter boundary. The agent’s diagnostics separately tracks tool changes (`src/agent/agent.ts:654-680`).

### Message prefix and dynamic snapshot

Persisted history is translated into provider messages in its original chronological order. User and assistant content are reconstructed, tool results become user messages containing `tool_result` blocks, and summaries represented as system messages become user context messages (`src/agent/context.ts:32-103`). The agent creates a new user row for the current input, then loads active history (`src/agent/agent.ts:351-361`).

Dynamic providers are built into a map once per agent (`src/agent/agent.ts:120-131`, `src/agent/agent.ts:157-158`). The production composition registers dynamic sources including rate-limit and MCP instructions when present, activity, recall, skills, working memory, prediction, scheduling, subconscious context, and introspection (`src/index.ts:1090-1169`). During a turn, skills are retrieved once and dynamic provider values are assembled into a snapshot once, when the latest message is a string-content user message (`src/agent/agent.ts:438-457`, `src/agent/agent.ts:489-509`). The snapshot algorithm emits a full snapshot on first use or reset, a delta for changed provider output or provider-key removals, and a noop when hashes are unchanged (`src/agent/snapshot.ts:65-103`, `src/agent/snapshot.ts:105-145`). The agent builds the provider map once per instance (`src/agent/agent.ts:157-158`), so a provider disappearing from that map is not an ordinary live-turn change; the snapshot helper’s removal path is available if the map passed to it has fewer keys, but this wiring does not rebuild the map on each turn.

A full or delta snapshot is attached to that user message. A noop or empty attachment leaves it plain. Removed-provider notices are added to the attachment when `removedProviders` is nonempty (`src/agent/messages.ts:19-27`, `src/agent/messages.ts:43-77`). The composed content is persisted onto the current user row and copied into in-memory history, so later requests replay the same bytes rather than regenerating a different attachment for that earlier turn (`src/agent/agent.ts:499-509`). Provider output changes and any removal notices that are produced therefore affect the *current request’s message suffix*; they do not rewrite previously persisted user messages. The snapshot state resets after a successfully committed compaction (`src/agent/agent.ts:560-570`), so the next composition starts with a full snapshot and is a known point where message-prefix reuse is interrupted.

At each request the message marker is placed at the end of whichever message is currently last. On the initial request this usually means the current user message (including any snapshot attachment); after a tool batch it may instead be the latest user-role tool-result message. As a conversation proceeds, later turns append messages after prior turns, while the latest marker moves to the current end. This is the intended incremental-prefix shape: previously cached completed content remains before the new suffix when the system/tool prefix and earlier history remain identical. Cache continuity can still be lost if old history is removed or reshaped, such as through compaction or context-budget exchange shaping (`src/agent/agent.ts:459-481`, `src/agent/agent.ts:513-651`).

## Issues and inefficiencies found

1. **No evident wasted marker in steady state.** The system marker secures the reusable tools+system prefix, and the final-message marker secures the request’s current conversation end. Both are applied centrally for complete and stream calls (`src/model/anthropic.ts:99-114`, `src/model/anthropic.ts:223-243`, `src/model/anthropic.ts:295-315`).
2. **The final marker is intentionally volatile in position.** It follows the latest message rather than a fixed role or fixed historical turn boundary. This is useful for advancing the cached conversation checkpoint; it also means there is no invariant that it always lands on a user message or on a completed turn. A request ending in a tool result will mark that result’s last content block (`src/model/anthropic.ts:76-86`; history role conversion at `src/agent/context.ts:79-90`). No demonstrated correctness or hit-rate failure justifies changing it.
3. **Tool order is an avoidable source of prefix variation.** `toModelTools()` follows registry insertion order, and the adapter preserves it (`src/tool/registry.ts:147-177`, `src/model/anthropic.ts:116-124`). If order changes while definitions are otherwise equal, the system-prefix cache identity may change. Whether canonical sorting would be behavior-preserving for model selection/tool behavior should be evaluated before changing it.
4. **System prompt is reconstructed each round.** Memory core blocks are fetched and formatted each call, and the agent appends diary text each round (`src/memory/manager.ts:59-71`, `src/agent/agent.ts:397-403`). It is intended to be stable but is not memoized. This is overhead and a possible source of accidental prefix changes if the underlying core state changes mid-turn; it is not a reason to cache stale system content in the adapter.
5. **Snapshot deltas do not preserve a standalone full current snapshot in every user turn.** By design, delta messages contain changed sections only, while noop omits an attachment and removal-only deltas carry a removal notice (`src/agent/snapshot.ts:105-145`, `src/agent/messages.ts:55-71`). This can make the current user message differ between turns, but earlier content remains persisted and byte-stable. It is not an adapter breakpoint defect; improving the user-message arrangement would require changes outside the adapter-only scope.
6. **No dynamic content is placed after a marker within its marked block.** The system marker follows the complete concatenated system text; the message marker is applied only after all content blocks for the final message have been normalized (`src/model/anthropic.ts:54-66`, `src/model/anthropic.ts:79-86`, `src/model/anthropic.ts:99-108`). Later request content follows the marker only in later request construction, as expected for incremental caching.

## Recommendations ranked by expected benefit ÷ risk

| Rank | Recommendation | Expected cache-hit impact | Risk | Safe to implement now? |
|---:|---|---|---|---|
| 1 | Keep the current two marker positions; retain the no-system fallback to one marker and no-message no-op behavior. | Preserves useful stable tool/system prefix and an incremental conversation checkpoint; avoids reducing the available reusable prefix. | Very low. Existing AC6.1/AC6.3 tests cover marker placement/count and edge cases (`src/model/anthropic.test.ts:440-603`, `src/model/anthropic.test.ts:605-664`). | **Yes.** No placement change is warranted. |
| 2 | Consider canonical tool-definition ordering in a separate change, with registry and model-behavior tests. | Could avoid tool-order-only invalidation of the system-prefix cache when registration order differs but definitions are equivalent. | Low-to-medium: reordering can affect provider-facing ordering and needs explicit compatibility testing; it belongs at the shared tool/request policy layer, not as an unreviewed Anthropic-only change (`src/tool/registry.ts:147-177`, `src/model/anthropic.ts:116-124`). | **No.** Defer to a scoped change with tests and observed need. |
| 3 | Consider caching or snapshotting the core system prompt at an appropriate turn boundary, while keeping intentional mid-turn updates explicit. | May reduce repeated core-block fetch/format work and prevent unintended within-turn system-prefix variation. | Medium: stale prompt risk if memory changes during a turn or if refresh semantics are wrong; request assembly and memory lifecycle need coordination (`src/agent/agent.ts:397-403`, `src/memory/manager.ts:59-71`). | **No.** Requires agent/memory work outside the permitted file scope. |
| 4 | Add an additional breakpoint only if a measured workload identifies a useful intermediate, stable prefix (for example, a boundary before a large volatile suffix). | Potentially helpful only for that workload; current common path uses two of four available markers. | Medium/high: extra markers can waste the budget or pin volatile content; no measured need or current insertion point justifies it. | **No.** Defer pending trace evidence and explicit boundary design. |

## Applied vs deferred

**Applied now:** No code or test changes. The audit found no low-risk breakpoint placement adjustment justified within `src/model/anthropic.ts`. The current system marker is already at the end of the system content, and the final-message marker already marks the latest complete content block. Moving either one without changing request assembly would sacrifice a useful cache prefix or mark a less stable boundary. Existing behavior is kept unchanged.

**Deferred:**

- Canonical tool ordering: deferred because it changes provider-facing order and should be tested at the registry/shared request layer rather than imposed only by Anthropic (`src/tool/registry.ts:147-177`, `src/model/anthropic.ts:116-124`).
- System-prompt memoization: deferred because safe invalidation depends on core-memory and diary update semantics; adapter-local caching could serve stale instructions (`src/agent/agent.ts:397-403`, `src/memory/manager.ts:59-71`).
- Use of a third or fourth breakpoint: deferred because no stable intermediate boundary with expected benefit was found, and the existing two markers already capture the common stable prefix and current conversation end (`src/model/anthropic.ts:60-66`, `src/model/anthropic.ts:76-86`).
- Changes to dynamic-context snapshot or persisted-history placement: deferred because those behaviors are owned by agent/context composition, outside the adapter-only safe scope (`src/agent/agent.ts:489-509`, `src/agent/messages.ts:55-71`).
